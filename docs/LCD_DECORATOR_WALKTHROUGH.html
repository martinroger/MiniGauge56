How the LCD decorator got ~40% cheaper

The 1.75" AMOLED is made to look like a dot-matrix LCD. Every tile LVGL draws is shrunk into 3×3 dots, tinted amber and sent to the panel. This page explains each change made to that path: what it does, why it is faster, and what the board measured.

1 · The path of a tile

LVGL does not draw the whole 466×466 screen at once. It renders tiles: strips 466 pixels wide and up to 50 lines tall (23,300 pixels). Each finished tile is handed to a flush callback. The decorator replaces that callback, rewrites the tile into the dot-matrix look, then calls the original callback so the panel driver can send it out.

Three facts about this board decide where the time goes:

  1. PSRAM is slow and shared. It sits on an 80 MHz octal bus behind a cache. Reads that miss the cache and writes that evict lines cost far more than the same work in internal RAM.
  2. The flush is asynchronous. esp_lcd_panel_draw_bitmap() starts a DMA and returns. LVGL waits for flush_ready (fired from the DMA-done interrupt) before it touches the draw buffer or sends another tile. That wait is what makes a single output buffer safe.
  3. The LVGL task holds a lock (esp_lv_adapter_lock) for the whole refresh cycle: every tile of a frame is rendered, decorated and flushed inside it. Anything else that wants LVGL waits.

2 · The decimator: pixels into dots

The emulated LCD has far fewer dots than the panel has pixels. With cell_size 3 and gap_size 1, a 3×3 block of pixels becomes one dot: a 2×2 lit area and a 1-pixel gap on the right and bottom. 466 px therefore gives about 155 dots across. For each cell the kernel averages the luminance of the 2×2 pixels it covers, maps that to a colour between the palette's inactive and active shade, and paints the dot.

What came first (commit 2762974)

The first version already removed two full passes. Earlier, the 8-bit tile was decimated in place, then a second loop expanded it to 16 bits. Now one function, lcd_emulator_apply_filter_8to16, reads the 8-bit tile read-only and writes 16-bit pixels straight to the output. It also swaps the two bytes of each pixel as it writes, because the panel expects big-endian on the wire and LVGL's usual swap step is skipped for 8-bit data. That fixed the earlier "black shows as green" colour bug.

3 · Four kernel tricks (commit 3265c5f)

The output is bit-for-bit identical to the straightforward version. A host fuzz test (200,000 random cases) and the 11 host suites check that. The speed comes from doing less work per pixel.

① Build one row, copy it

All pixel rows inside one dot row of a cell band are identical: the same run of dot colours, then gap pixels. The kernel builds that row once per band (the amber row in the figure above), then memcpys it for the remaining dot rows. Gap rows are a single constant colour, written with 32-bit stores two pixels at a time. The old loop did a modulo and a division for every output pixel to decide "gap or dot?"; the new one never asks.

② Tint ramp: 256 colours looked up, not computed

Turning an average luminance into a shade between inactive and active colour takes three multiplies, three rounded divisions by 255 and three clamps. There are only 256 possible inputs. When a tile has at least 384 cells, the kernel builds a 256-entry table once, on the stack (512 bytes), then each cell does a single indexed load. Small tiles skip the table, because building it would cost more than it saves.

③ Divide by multiplying

The average of a dot is sum / count, and a division is slow on the ESP32-S3. For a count c the kernel precomputes r = ⌈2²⁴ / c⌉ and uses (sum · r) >> 24. That equals the exact integer division for every sum a dot can have (0…255·c) as long as c ≤ 255; the test checks every sum. Try it:

④ Skip the identity table

RGB232 input needs a table to turn a colour byte into luminance. LVGL 9's L8 format is luminance, so the table lookup was pure overhead. L8 input now reads the byte directly.

Measured effect of ①–④ together (PR build vs baseline, 8-bit grayscale, tinted, amber): boot repaint 173k → 104k µs per Mpx, idle 184k → 133k, swiping 183k → 110k.

4 · The staging tile (commit e56da01, default on in 19093f9)

CONFIG_LCD_EMULATOR_STAGING_INTERNAL moves the output buffer. Before: one 434 KB RGB565 buffer for the whole frame, in PSRAM. After: one 46.6 KB buffer for a single tile, in internal DMA-capable RAM.

How it is sized and why it is safe

  1. Size. At init the decorator reads the draw buffer's size (buf_1->data_size ÷ bytes per pixel = 23,300 px) and allocates exactly that many RGB565 pixels with MALLOC_CAP_INTERNAL | MALLOC_CAP_DMA: 46,600 bytes. On the board the log reads "Internal staging tile: 23300 px (46600 B)".
  2. One buffer is enough. LVGL will not call the flush callback again until flush_ready fires, and the adapter fires that from the DMA-done interrupt. The DMA has therefore finished reading the staging tile before the next tile overwrites it.
  3. Fallback. If a tile is ever larger than the staging buffer, the decorator allocates the old full-frame PSRAM buffer the first time it is needed and uses that instead. If the internal allocation fails at boot, it logs a warning and uses PSRAM from the start.
  4. Cost. About 35 KB less internal heap than before (the PSRAM buffer is no longer allocated up front), and the largest contiguous free internal block drops from 167,936 to 135,168 bytes.

Why both flush and decorate got faster

The wrapped flush call (orig_flush) dropped by about 40%: it now hands the panel driver a buffer in internal RAM, so the driver's per-tile work and the QSPI DMA read no longer go through the PSRAM bus the CPU is using. The decorate step gained 10–25%, most likely because its writes no longer compete with the 8-bit source reads for the PSRAM cache and bus (I measured the effect, not the mechanism). With the filter off (passthrough LUT) the gain is larger, about 37k → 29k µs per Mpx, since that path is almost pure memory traffic.

5 · The profiler that produced these numbers

CONFIG_LCD_EMULATOR_PROFILE (default off, compiled out entirely) wraps the flush callback and prints one PROF line per second:

PROF 1.00s tiles/s=96.0 px/s=1815620 avg_px/tile=18913 max_px/tile=23300 fps=12.0 bypass=0 migrated=0
 | decorate us/tile=3451.7 us/Mpx=182504 | orig_flush us/tile=351.4 | finish_latency us/tile=358.8
 | lvgl_stack_hwm=2536 B (lvgl) heap_int_free=187119 largest=135168
  • decorate and orig_flush use the CPU cycle counter (CCOUNT) read before and after each step.
  • finish_latency is the time from starting the flush to LVGL's LV_EVENT_FLUSH_FINISH. It uses the shared esp_timer clock, because the event fires from an interrupt that can run on either core.
  • The first runs were wrong. The LVGL task has no core affinity. The two cores have separate CCOUNT registers, so a task that migrated mid-tile produced a negative delta, which unsigned arithmetic turned into ~17.9 s (the 591,810 µs/tile values). The profiler now drops any sample whose delta looks negative and counts them in migrated=. All published numbers come from the fixed profiler.
  • Stack check. lvgl_stack_hwm is uxTaskGetStackHighWaterMark of the LVGL task: 2.5–2.8 KB used out of its 8 KB, with the decorator active.

6 · IRAM placement: tried, measured, dropped

The project runs code from PSRAM (SPIRAM_XIP_FROM_PSRAM), so instruction fetches go through the same cache as data. I added CONFIG_LCD_EMULATOR_HOT_IN_IRAM, which put the whole decimator (all helpers are inlined into one function) into internal instruction RAM.

It helped at idle by about 7% (133k → 124k µs per Mpx), but while swiping, the numbers did not move beyond noise (103–126k vs the PR build's 108–111k). Combined with staging it matched staging alone. For about 8 KB of internal RAM, that was not worth keeping, so commit 19093f9 removed the option.

Reading: once the data path is the bottleneck (reading the 8-bit tile from PSRAM), faster instruction fetch barely matters. What remains is mostly the PSRAM read of the source tile. Moving LVGL's draw buffer itself into internal RAM would be the next big step, but a 23 KB 8-bit tile × 2 buffers competes with everything else for internal heap.

7 · The boot-time lock race

With staging on, the board logged esp_lv_adapter_lock: Failed to acquire LVGL lock at about 2.7 s on 13 of 15 boots, and the "Backlight on" line was missing. The PR build without staging never showed it (0 of 15). Adding timestamps showed the cause was not in the staging code.

Why staging exposed it

The adapter loop is take lock → lv_timer_handler() → release → wait up to N ms for a notification. In the failing boots that wait returned immediately, because the next cycle's request came 14 µs after the release. I did not identify what posts the notification that cuts the wait short. The pattern is clear, though: the staging tile changes the timing of the end of a cycle, and in the PR build the loop paused long enough for wakeDisplay() to get the lock after 66 ms on all 15 control boots. Without staging, the boot path worked by luck of timing, not by design.

The fix is a longer wait: wakeDisplay() in main/main.cpp now uses WAKE_DISPLAY_LOCK_TIMEOUT_MS = 500 instead of 100 ms. The first-frame render takes about 135 ms with the lock held, so any short timeout at boot is fragile. The adapter's loop behaviour (re-taking its own lock within microseconds) is vendor code and I did not change it, but it can starve other short-timeout callers during heavy render bursts, so it is worth reporting upstream.
